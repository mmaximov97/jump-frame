# Серверная детекция позы: плюмбинг через ai-lab (без интеграции в физику)

## 1. Проблема

Сегодняшнее офлайн-сравнение подтвердило: RTMPose (`lightweight`, через `rtmlib`) находит
скелет на 100% кадров, где все три тайера MediaPipe (`lite`/`full`/`heavy`) проваливаются
полностью — 52/52 и 31/31 на двух реальных сложных клипах (вид со спины, бег, смаз), за
63мс/кадр даже на голом CPU без GPU. Этот пайплайн (детектор YOLOX + модель позы RTMPose) не
затащить в браузер через WASM так же просто, как MediaPipe — нужен серверный инференс.

У пользователя уже есть `ai-lab` — свой self-hosted AI-gateway (`/home/cypher/Projects/ai-lab`,
TypeScript, Docker Compose, GPU-хост) с рабочим паттерном для ровно такой задачи: async job API
(`POST /v1/jobs`, `GET /v1/jobs/:id`, `GET /v1/jobs/:id/output`), API-ключи со scope'ами
(`chat`/`stt`/`tts`/`voice_clone`/`admin`), очередь на BullMQ+Redis, отдельные Docker-контейнеры
под каждый бэкенд (Whisper, XTTS, Fish Speech, Qwen TTS), и уже готовый пример именно такой формы
задачи — `POST /v1/audio/transcriptions/async` (до 2 ГБ, файл стримится на диск, задача
становится в очередь).

## 2. Решение в двух словах

Завести на `ai-lab` новый job-тип `body_detection` строго по образцу
`audio.transcription.async`: клиент (FrameJump) грузит zip с уже извлечёнными кадрами клипа,
получает `job_id`, поллит статус через существующий generic job API, получает результат — массив
лендмарок по каждому кадру. Новый лёгкий Python-сервис на `ai-lab` — тонкая обёртка над
`rtmlib`'s `Body(mode='lightweight')`. Это ТОЛЬКО труба: цель — увидеть, что кадры реально уходят
на сервер и landmarks реально приходят обратно. Что дальше делать с этими landmarks (переделка
физики под 17 точек COCO без глубины, интеграция в `measureJump`) — отдельный, ещё не
спроектированный бриф.

## 3. Ключевые решения и их обоснование

### 3.1. Async job, не синхронный запрос

Обработка клипа в 150-300 кадров — это секунды даже на CPU, и заметно быстрее на GPU `ai-lab`,
но всё равно не мгновенно и не гарантированно укладывается в один HTTP-таймаут. `ai-lab` уже
решил эту задачу для похожего по форме случая (`audio.transcription.async`) — переиспользуем тот
же паттерн, а не изобретаем синхронный вариант, который придётся чинить при первом же долгом
клипе.

### 3.2. Zip с кадрами, не видеофайл

Клиент уже сегодня извлекает кадры через canvas для MediaPipe (`usePoseDetection.ts`'s `scan()`).
Переиспользуем это — грузим уже извлечённые JPEG-кадры плюс манифест времён, не сырое видео.
Меньше данных на проводе (JPEG на кадр компактнее целого видеофайла с лишними кадрами и звуком),
и на сервере не нужно решать вопрос с декодированием видео (кодеки, контейнеры, звуковая
дорожка) — только уже готовые изображения. Формат архива: `manifest.json`
(`[{ index: number, time: number }]`) плюс `frame_0000.jpg`, `frame_0001.jpg`, ... — имя файла
кодирует `index`, порядок кадров в `manifest.json` авторитетный.

### 3.3. Отдельный, честный формат ответа — не притворяемся `PoseFrame`

RTMPose даёt 17 точек в порядке COCO (nose, left_eye, right_eye, left_ear, right_ear,
left_shoulder, right_shoulder, left_elbow, right_elbow, left_wrist, right_wrist, left_hip,
right_hip, left_knee, right_knee, left_ankle, right_ankle), без глубины (z). Текущий
`PoseFrame`/`ComTrack`-пайплайн в `src/lib` построен на 33 точках MediaPipe BlazePose с
глубиной — `computeFootY` медианит 6 точек стопы (лодыжки+пятки+носки), которых у COCO попросту
нет (только 2 лодыжки). Ответ сервера — новый, отдельный тип
(`BodyDetectionFrame: { time: number, landmarks: { x: number, y: number, score: number }[] }`,
ровно 17 точек), никак не подгоняемый под `PoseFrame`. Переделка физики под этот формат —
отдельный бриф; в рамках этого брифа результат просто показывается (лог/примитивный
дебаг-вывод), не скармливается `measureJump`.

### 3.4. Scope `body_detection`

Новый API-key scope, по аналогии с уже существующими `chat`/`stt`/`tts`/`voice_clone` (не
широкий `vision` — по вашему решению) — только для этого нового job-типа.

## 4. Компоненты

### На `ai-lab` (`/home/cypher/Projects/ai-lab`)

- Новый Python-сервис (Docker-контейнер, как `whisper`/`xtts`/`fish-speech` сегодня) — обёртка
  над `rtmlib`'s `Body(mode='lightweight', backend='onnxruntime', device='cuda')` (GPU на
  проде, `cpu` — фолбэк). HTTP-эндпоинт: принимает один кадр (или батч), отдаёт keypoints+scores.
- `src/clients/body-detection-client.ts` — новый клиент, по образцу `WhisperClient`
  (`src/clients/whisper-client.ts`), вызывает Python-сервис.
- `src/jobs/job-types.ts` — новая Zod-схема `bodyDetectionJobSchema`, новый вариант в
  `jobCreateSchema`'s `type` enum: `"body_detection"`.
- `src/routes/body-detection-routes.ts` — новый роут `POST /v1/vision/body-detection/async`, по
  образцу `/v1/audio/transcriptions/async` (`src/routes/audio-routes.ts`): принимает multipart
  zip, стримит на диск, создаёт job через `createQueuedJob`.
- `src/jobs/worker.ts` — новая ветка обработки для `type === "body_detection"`: распаковывает
  zip, гоняет каждый кадр через `BodyDetectionClient`, собирает результат, кладёт как output
  job'а — по образцу того, как уже обрабатывается `audio.transcription`.
- Новый API-key scope `body_detection` в существующей системе scope'ов (`src/auth`).

### На FrameJump (`jump-measurer`)

- Новый composable (например `src/composables/useServerBodyDetection.ts` — не `src/lib`,
  поскольку упаковка в zip и сетевые запросы требуют браузерных API, что нарушает чистоту
  `src/lib/**`): берёт уже извлечённые кадры (переиспользует `scan()`'s результат из
  `usePoseDetection.ts`, не дублирует логику извлечения), пакует в zip через `JSZip` (новая
  зависимость), грузит на `/v1/vision/body-detection/async`, поллит job раз в ~1-2с, получает
  результат.
- Дев-путь для проверки трубы (кнопка/страница, точное место — деталь реализации, не
  архитектурное решение) — просто показывает/логирует полученные landmarks, не встраивается в
  основной флоу измерения.

## 5. Поток данных

`useServerBodyDetection`'s dev-путь → переиспользует уже извлечённые кадры → `JSZip` пакует
кадры+манифест → `POST /v1/vision/body-detection/async` (multipart, API-ключ со scope
`body_detection`) → `ai-lab` стримит zip на диск, создаёт job, кладёт в очередь → воркер
распаковывает, гоняет кадры через новый Python RTMPose-сервис, собирает результат → клиент
поллит `GET /v1/jobs/:id`, при `status: "completed"` забирает `GET /v1/jobs/:id/output` → дебаг-
вывод в консоль/на экран.

## 6. Обработка ошибок и границы

- Сервер недоступен / сеть упала при загрузке — явная ошибка, без клиентского fallback (решено
  ранее: «все видео всегда через сервер»).
- Job зависла/упала на стороне `ai-lab` — воркер уже умеет ретраить (см. `job-service.ts`'s
  `attempts: 3, backoff: exponential` — переиспользуется как есть, не переделывается).
- Таймаут поллинга на клиенте — если job не завершилась за разумное время (например 2 минуты),
  показать ошибку, не ждать бесконечно.
- Слишком большой zip (очень длинный клип) — ограничение по аналогии с `ASYNC_UPLOAD_SIZE_LIMIT`
  в `audio-routes.ts` (2 ГБ) — для кадров этот лимит практически недостижим при разумной длине
  клипа, отдельно не сужаем.

## 7. Что не входит в эту итерацию

Переделка `comTrack.ts`/`bodyModel.ts` под 17 точек COCO без глубины — отдельный бриф. Интеграция
результата в `measureJump`/`guessFlightWindow`/основной флоу приложения — тоже отдельно. UI для
управления API-ключом на клиенте — для дев-пути ключ берётся из переменной окружения/конфига, не
отдельная страница настроек. Выбор между CPU и GPU деплоем Python-сервиса на `ai-lab` — решается
при реализации по факту того, что реально доступно на хосте.

## 8. Тестирование

Ручная проверка end-to-end: реальный клип (`1.mp4`, тот самый сложный) → кадры извлекаются →
уходят на `ai-lab` → приходят обратно landmarks → визуально свериться, что на кадрах, где
MediaPipe сегодня не находит скелет вообще, RTMPose через новую трубу находит (то же самое, что
уже подтверждено офлайн-скриптом сегодня, но теперь через реальный HTTP-путь, а не Python-скрипт
напрямую). Автотестов на composable-часть не будет (политика проекта — композаблы не
покрываются), на стороне `ai-lab` — по принятым там соглашениям (не в скопе этого документа).

## 9. Открытые вопросы, не блокирующие эту работу

- Точный формат дев-пути на клиенте (кнопка/страница/консоль) — деталь реализации.
- GPU vs CPU деплой Python-сервиса на `ai-lab` — зависит от факта наличия свободного GPU-слота
  на хосте на момент реализации.
- Как масштабировать при нескольких одновременных клипах (лимиты очереди, конкурентные GPU-
  задачи) — не вопрос для дев-плюмбинга, но встанет при переходе в продакшен.
